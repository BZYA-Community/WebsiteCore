### 关于 servants 依赖注入与可测试性的设计

本文对应 issue #18：`internal/core` 反向依赖 `dao` 行结构体 + `internal/dao` 全局 service locator，导致 servants 层无法构造"带假 DAO 的实例"，全仓单测覆盖为零（#11 的技术根因）。本文记录**终态目标**与**分步落地计划**；当前 PR 只完成第一步（构造注入入口 + 样板单测），行为零变化。

### 场景

* 想给审核/权限/私信等业务规则补单测（#11），但 servant 只能通过 `base.NewDaoServant()` → `dao.DataService()`（`sync.Once` 后的包级变量）拿到依赖，测试里只能改全局，互相污染且依赖开发者本机 `config.yaml`。
* `internal/core/ms/ms.go` 里 `type User = dbr.User` 等全是别名，"领域层"整体 `import internal/dao/jinzhu/dbr`，想构造一个假的领域对象必须拼 GORM 行结构体。

### 需求

* servants 能通过构造函数显式接收 `core.DataService` 等依赖，不读取包级全局；
* 单测可以在干净检出（无 `config.yaml`、不调 `conf.Initial`）下用假 DAO 跑通业务逻辑；
* 生产装配路径保持不变，逐步迁移，不产生行为变化。

### 方案（分步）

1. **（本 PR，已落地）构造注入入口 + 样板单测**
   以 `internal/servants/web/followship.go` 为样板，新增 `NewFollowshipService(ds core.DataService) api.Followship`：
   直接用字面量组装 `&base.DaoServant{BaseServant: base.NewBaseServant(), Ds: ds}`，绕开 `dao` 的全局定位器；
   `RouteWeb -> newFollowshipSrv` 的既有全局装配路径原样保留。
   配套 `followship_test.go` 提供手写假 DAO：`struct { core.DataService }` 内嵌 nil 接口、只覆写被测方法，
   未覆写的方法被调用即 panic，从而零配置运行单测。
2. **领域类型收口**：把 `core/ms` 的类型别名改为 `core` 自有结构体，`dao` 负责与 `dbr` 互转；
   或明确接受 `dbr` 作为唯一模型、直接删掉 `core/ms` 这层假抽象。
3. **移除 service locator**：去掉 `internal/dao/dao.go` 的 `sync.Once` 全局，组装上移到 `cmd` / `base.NewDaoServant`，
   所有 servant 构造函数收敛为显式注入。
4. **清理死代码**：删除 `sakila` / `slonik` 包或用 build tag 隔离（当前实现只有 `logrus.Fatal("not support now")`）。
5. **补测试**：1-3 完成后按 #11 的计划补权限/审核/私信规则单测。

### 疑问

* 第一步只开了一个口子：除 followship 外的 servant 仍走全局路径，`web` 包内 `_ds/_ac/_wc/_siteSettings`、
  `chain` 包内 `_ums/_ac`、`conf` 约 50 个包级 `*Setting` 变量都还在，需按 2-3 步逐个收口。
* `core/ms` 别名一旦改自有结构体，会波及 `dao`/`base`/`web` 大量调用点，需要单独一个 PR 并配套比对测试。
* `base.NewBaseServant()` 目前仍会读 `conf.UseSentryGin()`（未初始化时安全返回 false），
  彻底去 conf 依赖可作为第 3 步的一部分。
