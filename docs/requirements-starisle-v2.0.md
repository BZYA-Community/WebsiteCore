## 1. 产品概述

### 1.1 定位

starisle 是一个面向青少年与教师的**学习协作平台**，围绕四类内容组织：学生做的**项目**、老师开的**课程**、平台发布的**专栏**、可被申请指导的**导师**；并以**营**作为组织线下活动的容器。

平台**不托管代码**，项目仓库以外链形式引用。

### 1.2 本期交付物是一个 demo

⚠️ **这一点决定了本文很多取舍，实现前请先读懂。**

本期交付一个**用于对外演示**（投资人、合作学校、评审）的 demo，而不是面向真实用户开放的生产系统。具体含义：

| 方面 | 本期做法 |
| --- | --- |
| 注册、登录、人工审核 | **完整真做，不允许任何 bypass** |
| 标记 🕒 的功能 | 按钮存在且可点击，但点击后仅落库埋点，无后续流程 |
| 数据 | **全部虚构**，见 1.5 |
| 演示方式 | 现场双屏：一屏注册、一屏 admin 当场审核通过，见 1.4 |

### 1.3 目标用户

| 群体 | 说明 |
| --- | --- |
| 青少年 | 学生、营员，平台的主要内容生产者与消费者 |
| 教师 | 开设课程、参与项目、担任导师 |

⚠️ **目标用户包含未成年人**，这对实名信息处理、内容审核、公开页面范围有直接约束，详见 [6.7](#67-未成年人保护)。本文多处"为什么不做某件事"的理由都来自这一条。

### 1.4 演示动线

演示现场要能当着对方的面走通完整注册链路，因此：

1. 对方在一屏提交注册申请，填写真实姓名、邮箱、身份。
2. 系统发出邮箱验证信，对方点击验证。
3. 演示者在另一屏的 admin 后台看到这条申请，**当场审核通过**。
4. 系统发出激活邮件，对方点击、设置密码、登录成功。

⚠️ **对发信服务有硬要求**：邮件必须**秒级送达且不进垃圾箱**。裸 SMTP 直发不可接受，需使用信誉良好的发信服务。这是整个演示最容易翻车的一环。

### 1.5 演示数据

| 类型 | 做法 |
| --- | --- |
| 导师 | 虚构姓名、方向、介绍 |
| 老师、学生、营员 | 虚构 |
| 项目、课程、专栏、营 | 虚构 |

⚠️ **严禁使用任何真实未成年人的信息**，包括"在真名基础上略作改动"。演示数据会出现在所有演示场合，且不受平台的实名保护策略约束。

⚠️ 演示数据需**可被整体识别与清除**（例如统一打标），避免在转入真实运营时与真实数据混杂。

### 1.6 规模与容量

| 指标 | 目标值 |
| --- | --- |
| 注册用户总量 | ≤ 5,000 |
| 同时在线 | ≤ 500 |
| 数据量级 | 项目 / 课程 / 专栏均为千级以内 |

该规模下**无需分库分表、无需引入搜索引擎中间件**，单库 + 数据库全文索引（或 `LIKE` + 索引）即可满足本文的全部搜索需求。

### 1.7 一期范围

**做**：账号体系（双通道）、项目、课程（含选课关系）、营（后台管理 + 资料区）、专栏、导师、公开个人主页、主页、内容审核后台、站内通知。

**不做**：见第 10 章。

## 2. 角色与权限

### 2.1 角色

角色分为**平台管理角色**与**普通用户角色**两类，二者互斥——管理角色不产生 UGC、不出现在成员与导师列表中。

| 角色 | 标识 | 数量 | 说明 |
| --- | --- | --- | --- |
| 站主 | `manager` | 1–2 个 | 系统级配置（课程类别、导师方向、标签库），拥有全部权限 |
| 全站管理员 | `admin` | 多个 | 用户注册审核、UGC 审核、专栏发布、营与营资料的维护 |
| 普通用户 | `user` | — | 见下 |

普通用户按**身份**细分：

| 身份 | 标识 | 说明 |
| --- | --- | --- |
| 老师 | `teacher` | 可创建课程、参与他人课程授课、申请成为导师 |
| 学生 | `student` | 可创建项目、加入课程学习、向导师申请指导 |

⚠️ **「老师」在 starisle 内的含义比日常语义宽**：它指"具备授课或指导资质的成年用户"，**不要求实际开课**。外部请来的行业专家同样注册为老师。因此"一个没有任何课程的老师"是正常数据，不是异常。理由见 [ADR-0001](./adr/0001-external-experts-register-as-teachers.md)。

### 2.2 不是角色的三个东西

以下三者经常被误认为角色，本文明确它们不是：

| 概念 | 实际是什么 |
| --- | --- |
| **导师** | 老师身上的一个附加标记（`is_mentor`）。学生不能成为导师 |
| **营员 / 往期营员** | 由**参加记录**推导出的派生状态，不是账号上的字段。详见 4.3 |
| **选课学生** | 学生与某门课程之间的一层关系，不是账号身份 |

## 3. 账号体系

### 3.1 两条注册通道

账号有两个来源，**都是一等通道**：

```
【自助注册】任何人可发起

  提交申请 ──→ 待邮箱验证 ──点击验证链接──→ 待人工审核 ──admin 驳回──→ 已驳回
                                              │                      （附理由，可重新申请）
                                              └──admin 通过──┐
                                                             │
【名单导入】admin 批量导入，身份在导入时已确认                │
                                                             ▼
  admin 导入 ─────────────────────────────────────────→ 待激活
                                                             │
                              激活链接 7 天未使用 ──→ 失效（可申请重发）
                                                             │
                                          点击激活链接 + 设置密码
                                                             ▼
                                                         正常 ──admin 停用──→ 已停用
```

账号状态取值：`pending_email` / `pending_review` / `rejected` / `pending_activation` / `active` / `disabled`。

**关键设计点：**

1. **导入用户跳过人工审核。** 名单是 admin 自己导进来的，身份在那一刻就已确认，再排一次审核队列是重复劳动。导入后直接进入 `pending_activation` 并发出激活邮件。
2. **两封邮件职责不同，不可合并。** 第一封验证"邮箱确实是本人且可收信"，避免填错邮箱导致审核通过后激活信石沉大海；第二封才是激活。仅自助注册需要第一封。
3. **密码在激活环节才设置**，注册申请表不收集密码。账号未通过审核前，系统内不存在任何密码凭据。
4. **激活 token** 使用 ≥32 字节随机值，**哈希后入库**，一次性使用，有效期 7 天。
5. **驳回需填写理由**，通过邮件告知申请人；驳回后**允许用同一邮箱重新申请**。
6. **提供重发激活邮件与忘记密码**，二者复用同一套一次性 token 机制。
7. 审核队列展示申请人填写的全部信息，支持按申请身份筛选、批量通过。

### 3.2 注册表单字段

| 字段 | 老师 | 学生 | 可见性 | 说明 |
| --- | :---: | :---: | --- | --- |
| 真实姓名 | 必填 | 必填 | 见下方 ⚠️ | 2–20 字符 |
| 邮箱 | 必填 | 必填 | 仅平台 | 全站唯一，作为登录账号 |
| 申请身份 | 必填 | 必填 | 公开 | 老师 / 学生 |
| 用户名 | **不填** | 必填 | 公开 | 学生的对外展示名，全站唯一 |
| 任教科目 | 必填 | — | 公开 | 自由文本，≤50 字符 |
| 申请说明 | 必填 | 必填 | 仅平台 | 供 admin 判断是否通过，20–300 字 |
| 密码 | — | — | — | 激活环节设置，不在此表单 |

**老师的用户名默认等于真实姓名，且不可修改。**

⚠️ **真实姓名的可见性规则必须按下面这样理解，不能照字面读原始需求。** 原文说"真实姓名仅平台可查看"，但同时要求"老师用户名默认为真实姓名"、"导师卡片显示真实姓名"——这两条使老师的真实姓名事实上是公开的。正确的规则是：

> 真实姓名对**学生**严格保密，仅 admin / manager 可查看且访问留痕；**老师**在注册时即被告知"您的真实姓名将作为公开展示名"，属知情公开。

🕒 **不采集出生年份或年龄。** 后果是平台知道用户群体含未成年人，但**无法在系统内判断具体某个用户是否未成年**，因此"监护人同意"一类的策略暂时无据可依。若将来要做，需要补采。

### 3.3 登录

- 使用**邮箱 + 密码**登录。
- 仅 `active` 状态可登录；其余状态给出对应提示（待审核 / 已驳回 / 待激活，并提供重发激活邮件入口）。
- 登录安全要求见 [6.1](#61-认证安全)。

### 3.4 个人中心（自己看自己）

⚠️ 注意与 [4.6 公开个人主页](#46-公开个人主页)区分：个人中心是**自助操作台**，公开主页是**对外名片**，两者不是一个页面。

| 区块 | 内容 |
| --- | --- |
| 基本资料 | 用户名（老师不可改）、头像、个人描述；邮箱变更需二次验证 |
| 我的项目 | 我负责的 / 我参与的项目，含待处理的成员加入申请、待处理的课程收录请求 |
| 我的课程 | 我创建的 / 我参与授课的 / 我在学的课程 |
| 我关注的项目 | 收藏列表，可取消关注 |
| 我参加的营 | 进行中的营与往期的营，通往各自的营资料区 |
| 申请成为导师 | **仅老师可见** |
| 我的申请 | 各类申请的状态列表（加入项目、任教、成为导师、申请指导） |
| 账号安全 | 修改密码、登录设备 / 会话管理 |

## 4. 功能模块

### 4.0 通用约定

以下规则适用于全部内容模块，不在各节重复：

| 方面 | 约定 |
| --- | --- |
| 卡片列表 | 导航页以卡片网格展示，分页或滚动加载，每页 12–24 条 |
| 富文本 | 一律使用 **Markdown**，白名单渲染（见 6.3），不支持裸 HTML |
| 外链 URL | 仅允许 `http` / `https`，需格式校验；统一加 `rel="noopener noreferrer"` 并提示"即将离开 starisle" |
| 审核 | 所有 UGC 遵循第 5 章的审核状态机 |
| 搜索 | 大小写不敏感，支持中文分词或子串匹配，结果分页 |
| 时间 | 全站展示相对时间（"3 天前"），hover 显示绝对时间 |

### 4.1 项目（projects）

#### 列表页

卡片展示：项目名称、一句话简介、标签、成员头像（前 5 个）、关注数、更新时间；若已被课程收录，显示课程名。

**搜索**匹配范围：项目名称、简介、标签。

#### 详情页

| 内容 | 说明 |
| --- | --- |
| 项目名称 | 2–50 字符 |
| 一句话简介 | ≤100 字符，用于卡片展示 |
| 仓库链接 | 外链 URL，平台不托管代码，可为空 |
| README | Markdown 正文，见下 |
| 标签 | ≤5 个，见下 |
| 所属课程 | 可为空，见 4.1.4 |
| 成员列表 | 第一位为项目负责人（创建者），其余为成员。营员身份在此处以小标签形式展示 |
| 关注 / 取消关注 | 按钮，见 4.1.5 |
| 申请加入 | 按钮，见 4.1.3 |

#### 4.1.1 README 的定位

**README 是项目主页正文**，是详情页唯一的长文内容区，由项目成员编写维护，定位类似 GitHub 仓库首页。

编辑器提供模板骨架引导学生填写：

```markdown
## 这个项目在做什么
## 为什么做
## 目前进展
## 用到的技术
## 我们想找什么样的伙伴
```

⚠️ **不从仓库 URL 自动抓取 README。** 两个原因：服务端主动请求用户提交的 URL 会引入 SSRF（见 6.3）；抓来的内容绕过了平台审核。

#### 4.1.2 项目负责人与标签

- 中文展示统一使用**「项目负责人」**，数据库字段保留 `owner`。不使用"拥有者 / owner"作为界面文案——它强调所有权，而我们要表达的是主导与责任。
- **支持负责人转移**（毕业、退出等场景），转移后原负责人降为普通成员。
- 标签：**每项目 ≤5 个，每个 ≤12 字符**。标签来源是**站主维护的受控词表**，用户从中选择；允许提交新标签申请，经 admin 审核后入库。

> 标签不允许自由输入的原因：会迅速产生「AI / A.I. / 人工智能」这类同义碎片，使标签失去聚合价值。

#### 4.1.3 申请加入

用**结构化的三个小问题**替代一个大文本框，既降低学生的表达门槛，也便于负责人判断：

| 字段 | 必填 | 限制 |
| --- | :---: | --- |
| 我想加入的原因 | ✅ | 20–300 字 |
| 我能承担的部分 / 相关经验 | ✅ | 20–300 字 |
| 每周可投入的时间 | 可选 | 下拉：<5h / 5–10h / >10h |

申请状态：`pending` / `approved` / `rejected`。同一用户对同一项目**不可重复提交待处理申请**；被拒后设 **1 天冷却期**。

只有项目负责人能处理加入申请。

#### 4.1.4 被课程收录

项目可以被**一门**课程收录，表示"这个项目是在那门课里产生的"。

**流程是双向的：**

1. **课程老师发起**。老师在自己的课程后台，从**本课选课学生创建或参与的项目**里挑选。
2. **项目负责人确认**。收录请求出现在负责人的个人中心待办里，通过或拒绝。
3. 通过后，项目详情页显示"来自《XX 课程》"，课程详情页显示该项目。

⚠️ **学生不能自行把项目挂到任意课程下。** 课程页展示的产出是对外的门面，老师必须有控制权；同时收录对学生是曝光机会，所以也不能由老师单方面决定。两侧都要点头。

⚠️ **这条规则依赖选课关系存在**（见 4.2.3）。可选范围被限定在"本课选课学生的项目"，既是防乱挂，也让老师在一个短名单里挑选而不是全站搜索。

- 项目负责人可随时**解除**收录关系。
- 一个项目同时只能属于一门课程。

#### 4.1.5 关注项目

⚠️ **一期的「关注」是收藏，不是订阅——点了不会收到任何提醒。**

- 关注的项目聚合在个人中心的"我关注的项目"。
- 项目卡片显示关注数。
- 🕒 被关注项目更新时提醒关注者，一期不做，见第 10 章。

### 4.2 课程（courses）

#### 列表页

卡片展示：课程名称、类别、授课老师、节数、课时数、封面图。提供按**类别筛选**与关键词搜索。

#### 详情页

| 内容 | 说明 |
| --- | --- |
| 课程名称 | 2–50 字符 |
| 类别 | 单选，**选项由站主在后台维护** |
| 描述 | Markdown |
| 授课老师 | 可多位；创建者为第一位 |
| 节数 | **由课纲自动计算**，不手填 |
| 课时数 | 老师手填，用于对外宣传；系统另外自动展示"总时长 X 小时 Y 分钟" |
| 课纲 | 有序的"节"列表，见下 |
| 总资料包链接 | 可选，课程级外链 |
| 本课产出的项目 | 见 4.1.4 |

#### 4.2.1 课纲

每一节的字段：

| 字段 | 必填 | 说明 |
| --- | :---: | --- |
| 节名称 | ✅ | ≤50 字符 |
| 描述 | 可选 | ≤300 字符 |
| 主讲老师 | ✅ | 从该课程的授课老师中选择 |
| 时长 | ✅ | 以**分钟**记录 |
| 视频链接 | 可选 | 外链 URL |
| 资料链接 | 可选 | 外链 URL |

⚠️ **「节」和「课时」不是一回事。** 节是课纲里的一个条目；课时是对外宣传用的时长单位（通常 45 分钟一课时）。两者并存，不要在代码或界面里混用。

#### 4.2.2 「申请任教」（老师）

课程详情页上，当前用户是老师且不在该课授课老师之列时，显示**「申请任教」**按钮。

🕒 **一期点击后仅落库埋点，无后续流程**（沟通、联系方式交换属二期）。但**申请记录必须落库**，否则二期上线时没有任何存量数据。

> 改名说明：原始需求里叫"参与课程"。这个词从学生视角读同样成立，语义不够分辨，故改为「申请任教」——明确是"来教"，不是"来学"。

#### 4.2.3 「加入学习」（学生）✅ 本期真做

课程详情页上，当前用户是学生时，显示**「加入学习」**按钮。

⚠️ **这是本轮唯一一处从 TODO 清单里捞回来的功能。** 点击后**产生真实的选课关系**——该学生成为这门课的**选课学生**，进入课程的学员名单，授课老师可见。

必须真做的原因：4.1.4 的"从本课选课学生的项目里挑选"依赖这份名单。没有它，项目收录功能无法落地。

一期的实现范围就到"关系存在且可见"为止：

| 做 | 不做 |
| --- | --- |
| 学生加入 / 退出课程学习 | 🕒 师生沟通、聊天 |
| 授课老师查看选课学生名单 | 🕒 交换联系方式 |
| 个人中心的"我在学的课程" | 🕒 学习进度、作业、打卡 |

> 改名说明：原为"学习课程"。改为「加入学习」是因为"加入"暗示有后续动作，更像一个按钮，也与它现在真的会产生关系相符。

### 4.3 营（camps）✅ 本期新增

⚠️ **这一节在 v1.0 里不存在。** v1.0 只有一个叫"营员"的、与学生权限完全相同的空标签；本节把它背后真正的东西补上了。

#### 4.3.1 营是什么

**营 = 一次有起止时间的集中活动。** 每一期都是独立的一次活动，不是长期社群。

营**由 admin 创建和维护**。老师不能创建营——营对应线下活动，属于运营侧的事。

| 字段 | 说明 |
| --- | --- |
| 营名称 | 如"2026 夏季创客营" |
| 起止日期 | 决定营员身份的生效与失效 |
| 简介 | 营的说明 |
| 参加记录 | 该营的成员名单，由 admin 导入或添加 |
| 营资料 | 见 4.3.3 |

#### 4.3.2 营员身份是算出来的，不是存出来的

⚠️ **这是本节最容易实现错的地方。**

**参加记录**是一张关系表（用户 × 营），一个人**可以同时参加多个营**（暑期营 + 周末营完全可能并存），也可以先后参加多个营。

营员 / 往期营员**不是账号上的字段**，而是从参加记录推导出来的：

| 派生状态 | 推导规则 |
| --- | --- |
| **营员** | 该用户手上至少有一个**未结束**的营 |
| **往期营员** | 该用户参加过营，且当前**没有进行中**的营 |

因此：

- 营期结束时，营员**自动**变为往期营员，无需任何人操作。
- 原始需求里"学生和营员身份可以在 admin 批量转换"这条**不再需要**——它本来就是"营期到期"的手工替代品，现在由日期自动完成。admin 要做的只是维护参加记录。
- 往期营员**不会变回普通学生**，"参加过营"是永久的事实。

#### 4.3.3 营资料区

每个营有一个**营资料区**，承载该期营的课件、日程、成果等材料。

| 方面 | 规则 |
| --- | --- |
| 谁维护 | **admin**。老师和营员都不能上传 |
| 谁可见 | **仅该营的营员与往期营员**，以及 admin / manager |
| 游客与其他用户 | 完全不可见，营没有对外公开页面 |
| 是否需要审核 | **否**。由 admin 上传、admin 负责，与专栏同理，不进 UGC 审核队列 |

⚠️ **营资料区是往期营员"保留访问权"的落点。** 营结束后，往期营员仍可查看该期营的资料——这是"往期营员"这个状态的实际价值所在，不只是一枚徽章。

⚠️ **营没有对外公开的页面。** 营员名单是未成年人的聚合信息，公开展示正是 6.7 要避免的事。营在用户侧的全部可见形态只有两处：个人中心的"我参加的营"，以及项目成员列表上的营员小标签。

#### 4.3.4 营员标识的展示

营员 / 往期营员的标识以**小标签**形式出现在项目成员列表中，例如"2026 夏季创客营"。

- 老师能看到这个标识，但一期**不提供按营筛选**，也**不存在任何权限差异**——营员与学生的权限完全相同。
- 🕒 按营筛选、向某个营定向发通知、营员专属资源，均为后续可能的扩展。数据模型（参加记录）已经为此预留。

### 4.4 专栏（columns）

本质是平台博客，**仅 admin / manager 可发布**，普通用户只读。

| 字段 | 说明 |
| --- | --- |
| 标题 | 2–80 字符 |
| 作者 | **可多位**，关联平台用户（可点击跳转到其公开主页）；另有一个"外部作者"纯文本字段，用于署名非平台用户的撰稿人 |
| 封面图 | 可选，用于卡片展示 |
| 摘要 | ≤150 字符，用于卡片展示 |
| 正文 | Markdown |
| 发布时间 | 支持定时发布 |

专栏**不进入 UGC 审核队列**（发布者本身就是 admin），但保留"草稿 / 已发布"两态。

🕒 **一期不做**：评论、点赞、订阅。

### 4.5 导师（mentors）

导师是**老师身上的附加标记**，不是独立角色。学生不能成为导师。

#### 列表页

卡片展示：**真实姓名**、方向、描述摘要、头像。卡片上直接提供「申请指导」入口（仅学生可见）。点击卡片进入该导师的公开主页。

**搜索**匹配范围：姓名、描述。另支持**按方向筛选**。

#### 导师字段

| 字段 | 说明 |
| --- | --- |
| 真实姓名 | 公开展示（见 3.2 的 ⚠️） |
| 方向 | **受控词表**，由站主维护，可多选 ≤3 个。受控是"按方向筛选"能成立的前提 |
| 描述 | 导师自己撰写，50–500 字，**需审核** |

#### 4.5.1 怎么成为导师 ✅ 本期真做

**两条路都做：**

| 路径 | 说明 |
| --- | --- |
| **admin 直接标记** | admin 在后台把某个老师标记为导师。**这是 demo 里导师列表有内容的保证** |
| **老师申请 + admin 审核** | 入口在个人中心，需填写一段说明（50–500 字），进入 admin 审核队列 |

⚠️ v1.0 曾把"申请成为导师"整条推迟到二期，那会导致**导师列表永远是空的**——没有任何人能把老师变成导师。admin 直接标记这条路解决了它，申请流程则按"demo 要具备这些能力"的要求一并做出来。

#### 4.5.2 申请指导（学生）

入口在**导师卡片上**。学生填写一段说明（50–500 字）。

🕒 **一期点击后仅落库，无后续流程**——它的后续依赖聊天 / 联系方式能力。但申请记录必须落库。

同样设置**冷却期与频次限制**，防止学生批量骚扰导师。

### 4.6 公开个人主页 ✅ 本期新增

⚠️ **只有老师和导师有公开个人主页。学生没有。**

| 对象 | 是否有公开主页 |
| --- | :---: |
| 老师 / 导师 | ✅ |
| 学生 / 营员 | ❌ |
| admin / manager | ❌ |

**为什么学生没有**：一个聚合了"真实项目 + 参加过哪些营 + 时间段"的公开页面，等于把散落的信息拼成一个未成年人的画像。学生的营员标识就近显示在项目成员列表里即可，不做聚合页。

**老师 / 导师主页内容：**

| 区块 | 内容 |
| --- | --- |
| 基本信息 | 真实姓名（即用户名）、头像、任教科目、个人描述 |
| 导师信息 | 仅导师显示：方向、导师描述、「申请指导」按钮 |
| 开设的课程 | 该老师创建或参与授课的课程 |
| 参与的项目 | 该老师参与的项目 |
| 撰写的专栏 | 若其为某篇专栏的作者 |

这个页面是三处链接的落点：专栏作者、导师卡片、课程的授课老师。

### 4.7 主页

主页是**对外演示时的第一印象**，本期的核心交付物之一。

| 顺序 | 区块 | 内容 | 目的 |
| :-: | --- | --- | --- |
| 1 | 顶部 Hero | 一句话说明 starisle 是什么 + 注册入口 | 让访问者 5 秒内明白平台定位 |
| 2 | **课程与产出** | 一门课程 + 它收录的项目 | **主打区块**。这是平台结构上最有故事感的地方 |

⚠️ **不上主页的内容**：营（名单是未成年人聚合信息）、最新注册用户、任何实时动态。

| --- | --- |

## 5. 内容审核

**原则：所有 UGC 先审后发，且一期全部由人工审核。** 未过审内容对作者本人以外的任何用户（含游客）均不可见。

⚠️ **一期不引入 AI 审核。**

### 5.1 审核对象清单

| 内容 | 是否需审核 | 备注 |
| --- | :---: | --- |
| 项目名称、简介、标签 | ✅ | |
| 项目 README | ✅ | 长文，审核工作量最大 |
| 仓库链接等外链 URL | ✅ | 需人工确认指向合规站点 |
| 课程名称、描述、课纲 | ✅ | |
| 课程视频 / 资料链接 | ✅ | |
| 导师描述 | ✅ | |
| 用户名、个人描述、头像 | ✅ | 头像需图片审核 |
| **营资料** | ❌ | **由 admin 上传、admin 负责**，同专栏 |
| 专栏 | ❌ | 由 admin 自己发布 |
| 各类申请说明 | ❌ | 仅申请的接收方可见，不公开 |
| 项目与课程的收录关系 | ❌ | 双方都是已实名用户，互相同意即可 |

### 5.2 审核状态机

```
  草稿 ──提交──→ 待审核 ──通过──→ 已发布
                    │
                    └──驳回──→ 已驳回（附理由，可修改后重新提交）

  已发布内容被编辑：
  已发布 ──编辑并提交──→ 已发布（旧版本继续展示） + 待审的新版本
                              │ 通过 → 新版本替换展示
                              │ 驳回 → 保持旧版本展示，通知作者
```

**关键设计点：**

1. ⚠️ **编辑已发布内容时，旧版本继续对外展示**，新版本单独进入审核队列。绝不能因为一次改错字，整个项目页面就从站内消失。
2. 保留 admin 的**「快速通过」**操作，用于纯粹的小改动。
3. 审核队列需支持：按内容类型筛选、按提交时间排序、**并排查看新旧版本差异**。
4. 驳回必须填写理由，并通过站内通知告知作者。

### 5.3 工作量：demo 阶段成立，上线前必须重算

**demo 阶段人工全审的成本接近零**——演示数据全部虚构、由内部预先灌入，没有真实用户在产生内容，审核队列基本是空的。

⚠️ **但这个结论不能带进真实运营。** 按 5,000 用户、人均 3 条待审内容估算，总量约 15,000 条，其中 README 类长文单条审核耗时可达数分钟，粗算是 **100–250 人时的存量**，外加持续增量。

**这是本文唯一一个刻意留到后面的问题**（见 9.3）。真实开放注册前，必须用当时的 admin 人力重新算一遍，并决定是否接受下列缓解措施之一（它们都不破坏"先审后发"原则）：

- 接入**敏感词库**做前置自动过滤，命中直接驳回，不占用人工队列；
- 对**历史上从未被驳回过**的老用户，其小幅编辑走"先发后审"（可配置开关）；
- 审核队列支持批量通过；
- 引入 AI 初筛。⚠️ 注意这会把**未成年人写的内容发送给第三方服务**，选型时需要单独评估。

## 6. 安全要求

> 原始需求：「安全非常重要！非常重要！非常重要！」本章据此展开为可验收的具体条目。

### 6.1 认证安全

| 要求 | 具体做法 |
| --- | --- |
| 密码存储 | **bcrypt / argon2id** 加盐哈希，禁止 MD5 / SHA1 / 明文 |
| 密码强度 | ≥8 位，且不在常见弱口令库中 |
| 登录限流 | 同一账号连续失败 5 次锁定 15 分钟；同一 IP 失败 10 次触发验证码 |
| 会话 | Session Cookie 设置 `HttpOnly` + `Secure` + `SameSite=Lax`；登录后重置 Session ID（防固定会话） |
| 会话有效期 | 7 天，支持用户主动登出全部设备 |
| 二次验证 | **manager / admin 账号强制开启 2FA**——这是全站权限最高的账号 |
| 一次性 token | 激活、重置密码的 token：≥32 字节随机、哈希入库、一次性、有明确有效期 |
| 用户枚举防护 | 登录 / 找回密码的失败提示保持一致，不泄露"该邮箱是否已注册" |

### 6.2 授权安全

| 要求 | 具体做法 |
| --- | --- |
| 服务端强制鉴权 | **每个接口独立校验权限**。前端隐藏按钮不构成权限控制 |
| 越权防护（IDOR） | 所有按 ID 访问的资源，必须校验"当前用户是否有权访问该 ID"，而非仅校验登录态 |
| 实名信息访问 | 仅 admin / manager 可查看，**每次查看写入审计日志**（谁、何时、查了谁） |
| 管理操作审计 | 审核、封禁、导入名单、参加记录变更、导师标记、权限变更全部留痕，日志不可删除 |

**重点越权风险点**（逐条写测试用例）：

1. 审核他人项目的成员申请；
2. 编辑他人的项目 / 课程；
3. 通过 API 读取未过审内容；
4. 通过 API 读取他人实名信息；
5. 普通用户调用 admin 接口；
6. **非本营成员读取营资料区**——这是本期新增的、最容易漏的一条。营资料区没有公开入口，很容易让人误以为"拿不到 URL 就等于安全"；
7. **课程老师把非本课选课学生的项目强行收录**——前端下拉框做了限制，后端必须独立校验；
8. 学生伪造收录请求的同意方，替他人项目点通过。

### 6.3 输入与输出安全

| 风险 | 防护措施 |
| --- | --- |
| SQL 注入 | 一律使用 ORM 或参数化查询，禁止字符串拼接 SQL |
| **XSS** | Markdown **白名单渲染**：禁止 `<script>`、`<iframe>`、`on*` 事件属性、`javascript:` 伪协议；渲染后再过一层 HTML 消毒（如 DOMPurify）。**这是本平台最高危的风险点**——README、课程描述、导师描述全是用户可控的富文本 |
| CSP | 配置 `Content-Security-Policy`，禁止内联脚本，作为 XSS 的第二道防线 |
| CSRF | 所有写操作校验 CSRF Token，配合 `SameSite` Cookie |
| **SSRF** | ⚠️ 服务端**不得主动请求用户提交的任何 URL**（仓库链接、视频链接、资料链接）。这也是 4.1.1 拒绝自动抓取 README 的原因之一。若确需生成链接预览，必须走白名单域名 + 禁止内网地址段 + 禁止重定向 |
| 开放重定向 | 站内跳转只接受相对路径，不接受用户传入的绝对 URL |
| 文件上传（头像、营资料等） | 校验真实文件类型（不看扩展名）、限制大小、**服务端重命名**、剥离 EXIF、存储于独立域名或对象存储、禁止执行权限 |
| 参数校验 | 所有入参做类型 / 长度 / 范围校验，超长字段一律截断或拒绝 |

### 6.4 传输与部署

- **全站强制 HTTPS**，HTTP 自动跳转，开启 HSTS。
- 生产环境关闭 debug 模式与详细报错页（避免泄露堆栈与路径）。
- 数据库、Redis 等中间件**不对公网开放**。
- 应用使用**最小权限数据库账号**（不用 root）。
- 密钥、数据库口令通过环境变量或密钥管理服务注入，**禁止硬编码进仓库**。

### 6.5 数据安全

- 实名姓名等敏感字段**加密存储**（或至少做列级访问控制）。
- 日志、监控、错误上报中**脱敏**，不得打印密码、token、完整实名信息。
- 数据库**每日自动备份**，并定期演练恢复。
- 用户注销时，其 UGC **匿名化保留**：内容留下，作者显示为"已注销用户"。不做级联删除——项目是多人协作的产物，级联删除会把其他成员的心血一起删掉。

### 6.6 防滥用

| 接口 | 限流 |
| --- | --- |
| 注册申请 | 同一 IP 每小时 ≤3 次 |
| 登录 | 见 6.1 |
| 发送邮件（验证 / 激活 / 重置） | 同一邮箱每 10 分钟 ≤1 封，每日 ≤5 封 |
| 各类申请提交 | 每用户每日 ≤10 次 |
| 搜索 | 每用户每分钟 ≤30 次 |

注册环节加入**图形验证码或行为验证**，这是防批量注册的第一道关口。

⚠️ 邮件限流需要与 1.4 的演示动线一起测试——演示时会在几分钟内连续触发验证信和激活信，不要被自己的限流策略挡住。

### 6.7 未成年人保护

⚠️ 这是本平台区别于普通社区的核心约束。本文多处"为什么不做"的理由都指向这里。

| 要求 | 说明 |
| --- | --- |
| 最小化收集 | 除实名姓名与邮箱外，不采集身份证号、住址、电话；也不采集出生年份（见 3.2） |
| 真实姓名保护 | 学生的真实姓名**永不公开展示**，仅 admin / manager 可查看且留痕 |
| **学生无公开主页** | 见 4.6。不把项目、营、时间段聚合成一个可被外部浏览的未成年人画像 |
| **营不对外公开** | 见 4.3.3。营员名单是未成年人的聚合信息 |
| 禁止公开联系方式 | UGC 中出现手机号、微信号、QQ 号应在审核中驳回 |
| 无私信 | 一期不提供任何用户间私聊通道，天然降低风险 |
| 师生互动留痕 | 二期若开放联系方式交换，**必须平台留痕可追溯**，不可做成完全私密的通道 |
| 举报入口 | 一期就提供内容举报按钮，成本低但必要 |
| 演示数据 | 严禁使用真实未成年人信息，见 1.5 |

⚠️ **已知缺口**：因为不采集出生年份，平台**无法在系统内判断某个具体用户是否未成年**。上述措施都是"对全体用户一律从严"，而不是"对未成年人特殊处理"。若将来需要按年龄分级，必须先补采。

### 6.8 依赖与运维安全

- 依赖库定期执行漏洞扫描（`npm audit` / `pip-audit` 等），CI 中阻断高危漏洞。
- 及时更新框架与基础镜像。
- 上线前做一次**渗透测试或安全自查**，重点覆盖 6.2 的越权清单与 6.3 的 XSS。

### 9.3 唯一仍然开着的问题

**真实开放注册前，必须重新计算人工审核的工作量。** 详见 5.3。这个问题在 demo 阶段不成立（没有真实 UGC），但它会在转入真实运营时立刻变成瓶颈，届时需要当时的 admin 人力数据才能回答。

### 9.4 本文做出的假设

以下几点在讨论中没有被明确问过，本文按最保守的方式写入。**如与预期不符，这是最先要改的地方**：

1. **老师默认看不到营资料区**——本文未设"带营老师"这一概念，营完全由 admin 维护。
2. **一个项目同时只属于一门课程**——未讨论多课程收录的情形。
3. **「申请指导」「申请任教」的冷却期与频次**沿用 6.6 的通用限流，未单独定义。
4. **营资料的形态**按"文件上传 + 外链"处理，未讨论是否需要富文本正文。

## 11. 名词表

**名词定义以仓库根目录的 [`CONTEXT.md`](../CONTEXT.md) 为准**，本文不重复维护一份，避免两处走偏。

该文件当前收录 16 个词条，其中这几个最容易用错：

| 词 | 最常见的误用 |
| --- | --- |
| **老师** | 误以为一定开课。实际含义是"具备授课或指导资质的成年用户" |
| **营员 / 往期营员** | 误以为是账号上的字段。实际由**参加记录**推导 |
| **选课学生** | 与「学生」混用。它是学生与课程之间的**关系**，不是身份。不要叫"学员" |
| **关注** | 误以为是订阅。一期**不产生任何提醒**，就是收藏 |
| **节 / 课时** | 混用。节是课纲条目，课时是宣传用的时长单位 |
| **导师** | 误以为是与老师并列的角色。它是老师身上的一层标记 |
