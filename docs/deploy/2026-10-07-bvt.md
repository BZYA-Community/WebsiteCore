## Defect found and fixed: AliOSS ZIP MIME mismatch

Windows supplied the ZIP file-part MIME type `application/x-zip-compressed`. The backend correctly normalized this to `application/zip`, but the AliOSS upload policy required the canonical type while the browser still sent its file-part alias. The real bucket returned HTTP 403.

A controlled comparison with private synthetic objects isolated the cause:

| Request variant | Actual AliOSS result |
| --- | --- |
| Original browser ZIP alias against the canonical policy | HTTP 403 |
| Canonical `application/zip` file-part type | HTTP 200 |
| Browser ZIP alias plus canonical `x-oss-content-type` | HTTP 200 |
| Cleanup of the private comparison objects | HTTP 204 |

Alibaba Cloud documents that `x-oss-content-type` overrides the browser's file-part MIME type. The one-line production fix adds that canonical field to the existing signed form; its exact value is included in the policy alongside the existing type, object key, size, expiry, and private-ACL restrictions. See [AliOSS PostObject form elements](https://www.alibabacloud.com/help/en/oss/developer-reference/postobject).

Commit `752ff199` changes [course_uploads.go](../../internal/servants/web/course_uploads.go) and extends [TestCourseUploadCapabilities](../../internal/servants/web/course_uploads_test.go) to normalize the Windows ZIP alias and assert the override and its signed exact-value constraint. The regression failed before the fix and passed afterward. The corrected Linux binary was deployed; at 04:41:55 the same ZIP passed the real browser upload and verification flow.

The signed ZIP download additionally returned HTTP 200 with exactly 172 bytes and SHA-256 `4b6dda87e39a67998ee8f8b7edd7c771136ca22974b5d7a447a3b9d272a444a9`, matching the source fixture. Its unsigned URL returned HTTP 403. The video returned HTTP 206 for range `bytes 0–63/124612`; its unsigned URL also returned HTTP 403. These checks establish byte integrity and private-object enforcement for the synthetic files. The in-app browser could not provide a downloaded-file artifact because its child renderer failed, so browser download capture remains limited.

## Defect found and fixed: course-deletion refresh race

Deleting the synthetic course succeeded on the server but showed a not-found error during the subsequent catalog refresh. `loadGroups()` temporarily removed the course list from the rendered page; after it cleared its loading flag and before `loadCourses()` finished, Vue remounted the stale deleted course and requested its now-deleted lessons.

The [Courses.vue](../../web/src/views/Courses.vue) fix in committed and pushed revision `8c293db2` removes the confirmed-deleted course from the in-memory list before refreshing groups and courses, then shows the existing success message. A failed deletion still retains the course. The new [course-catalog.test.mjs](../../web/scripts/course-catalog.test.mjs) exercises Vue mount/unmount scheduling with an inert renderer: the old implementation failed because it reloaded the deleted course; the fix passes, preserves remaining courses, and verifies failed-delete retention. `npm run test:courses` includes this check, and the frontend production build passed. See the [verification log](../../custom/deploy-20261007/course-delete-verification.txt).

The clean Linux binary for `8c293db2` was deployed and its server-side SHA-256 matched the build. BVT-31 then repeated course deletion through the browser: the course disappeared, the success message appeared, and no course-not-found message appeared. The headless regression and the real browser retest therefore both passed.

## Defect found and fixed: disabled-session guest recovery

BVT-33 established that disabled-account code `20006` was mapped to HTTP 500 by the shared [HTTP error mapper](../../pkg/xerror/xerror.go). The existing frontend HTTP 401 interceptor therefore never cleared the old token. Reloading left the browser with empty guest menus, repeated 404 routes, and the disabled-account error when returning home.

Committed and pushed fix `efef7314` maps `20006` to HTTP 401, allowing the existing interceptor to clear the invalid token. Ordinary permission-denial code `20007` still maps to HTTP 403. The [user store](../../web/src/store/user.ts) also recovers the guest policy within its shared pending `loadSession()` promise, so concurrent callers finish the same recovery. Stale failures cannot replace a newer session, while genuine network errors and current-session 403 permission denials still reject without clearing a valid token. The router and request interceptor were unchanged.

The [backend regression](../../pkg/xerror/xerror_test.go) failed before the fix with HTTP 500 instead of 401 and passed afterward; affected backend tests, vet, and lint passed. The extended [frontend permission checks](../../web/scripts/permissions.test.mjs) reproduced failed bootstrap recovery before the store change, then passed concurrent recovery, stale-response/new-session protection, and network/403 preservation checks. Targeted frontend lint and production build passed. See the [before](../../custom/deploy-20261007/disabled-session-before.txt), [after](../../custom/deploy-20261007/disabled-session-after.txt), and [session-recovery](../../custom/deploy-20261007/session-recovery-verification.txt) evidence. The clean `efef7314` binary was deployed and BVT-33 passed using the browser with its existing disabled session. Guest catalog and public-home navigation recovered automatically; the test accounts were never re-enabled.
