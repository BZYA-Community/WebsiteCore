# Storage promotion and download verification

Course uploads have two object names: a client-writable staging key and a server-only final key. The upload completion transaction locks the attachment record, checks the object header and declared purpose, promotes the verified object, and commits the verified attachment. Deleting the staging object happens after the database commit. A database rollback leaves staging available for a retry.

## Shared attachments and deletion

Deleting a post, changing an avatar, rejecting an avatar, or rolling back a content submission removes or changes database references only. These actions never physically delete objects referenced by client-supplied or historical URLs: another user, post, course cover, or lesson may still use the same object. Failure cleanup may delete only a fresh object key generated by the server for that upload request. Course upload expiry separately removes its unverified staging objects and failed promotions; verified course resources are retained.

Published objects can therefore outlive their last reference. Automatic collection requires an authoritative reference inventory or reference counts, with transactional coordination across avatars, pending reviews, content, course covers, and lesson attachments. Such a collector is not implemented here. Do not apply age-only deletion to published objects or treat one deleted content record as proof that an object is unused.

## LocalOSS

Uploads write into a temporary file in the destination directory, check the exact byte count, sync and close the file, then publish with an atomic hard link. Publishing refuses to replace an existing object. Promotion creates another hard link and verifies that it refers to the inspected file. It does not copy a multi-gigabyte resource through application memory. The filesystem must support hard links and both names must reside on the same filesystem; NTFS was exercised by the tests below.

The local verification token is the immutable file's size and modification time. HTTP uploaders cannot modify an existing file through the upload API. The configured storage directory and operating-system account remain trusted; administrators must not edit stored files in place.

Downloads open regular files through Go's rooted filesystem API. Directory listings, symlinks, temporary files, and staging keys are unavailable. Private attachment paths require an unexpired HMAC signature. Windows path aliases (case variants, backslashes, trailing dots/spaces, and alternate streams) cannot bypass this check. Responses include `X-Content-Type-Options: nosniff`; non-video private attachments download with `Content-Disposition: attachment`. Video playback retains range and HEAD support.

Only the known `public` and legacy `image` namespaces permit unsigned reads; every other namespace requires a signature. This also closes alternate private namespace spellings such as NTFS short names, without relying on detecting every filesystem alias. A final route regression exercises existing files under an unclassified and short-name-like namespace and confirms unsigned access is denied.

## AliOSS

Inspection performs HEAD followed by a conditional GET of at most 512 bytes. Promotion binds the source key and ETag into server-generated destination metadata, requires an explicit private ACL, and rejects a destination already bound to a different source. Every copy includes the source ETag condition. An identical, private destination makes retries idempotent, including when OSS committed but its completion response was lost or malformed.

Objects above 1 GiB use 128 MiB server-side multipart copies. A 2 GiB resource uses 16 parts; resource bytes never pass through the application during promotion. Smaller objects use CopyObject. This is a conservative choice across OSS copy variants, not a claim that all current CopyObject requests have a universal 1 GiB limit. The [OSS copying guide](https://www.alibabacloud.com/help/en/oss/user-guide/copy-objects-16) and [CopyObject API](https://www.alibabacloud.com/help/en/oss/developer-reference/copyobject) describe the relevant variants.

The implementation follows [UploadPartCopy](https://www.alibabacloud.com/help/en/oss/developer-reference/uploadpartcopy) conditional source ranges and [CompleteMultipartUpload](https://www.alibabacloud.com/help/en/oss/developer-reference/completemultipartupload) completion semantics. Failed multipart operations are aborted. A response with HTTP 200 is insufficient: the final object's metadata, size, and ACL must also match. `x-oss-forbid-overwrite` is included, but OSS versioning can change that header's behavior. Correctness also depends on serialized completion under the attachment row lock and clients having no permission to write final keys.

Configure the bucket so staging and final course resources cannot become public through a bucket policy, website endpoint, CDN, or an external credential. Keep staging upload credentials scoped to the exact staging key. Configure an OSS lifecycle rule to abort incomplete multipart uploads after abandoned requests. A process killed during a local upload can leave an inaccessible `.upload-*` file; an operator may remove such abandoned files after ensuring no upload process still owns them.

## Reproducible checks

```sh
go test ./internal/dao/storage ./internal/servants/localoss -count=1
```

The storage tests run the pinned OSS SDK against an in-process HTTP transport, with no OSS credentials or network requests. They verify bounded reads, copy ranges, private ACLs, source ETag conditions, overwrite refusal, repeat completion, source changes between parts, failed completion, an error inside HTTP 200, an unknown completion outcome, and rejection of a public destination.

Local tests exercise real files: failed/short/oversized writes never publish, duplicate writes cannot replace data, promotion is repeatable, deleting staging preserves final data, symlinks and alternate streams are rejected, and a file with a 2 GiB logical size is inspected and promoted without reading its full contents. Download tests cover signatures, expiry, HEAD, range requests, private Windows path aliases, internal-file denial, and active content served as a download.

All checks passed on the development NTFS filesystem on 2026-10-07. The Windows agent sandbox denies hard-link creation; the same scoped tests passed outside that sandbox. This validates the implementation and SDK request contract. It does not substitute for a deployment smoke test against a real AliOSS bucket, its CORS policy, credentials, access policy, lifecycle rules, and CDN configuration.
