> 起草：@Alumin-Hydro · 2026-09-24。本章程中标注 ✅ 的条款已在仓库实际运行。
>
> **职责边界**：本章程只管"怎么协作、谁有权"——代码规范、审查机制、晋升制度、部署流程。
> 平台**做什么**（功能需求、角色权限、页面设计）以 [`requirements-starisle-v2.0.md`](./requirements-starisle-v2.0.md) 为唯一基线，本章程不重复定义。

## 一、代码规范

1. Commit 信息使用约定式前缀：`feat:`（新功能）/ `fix:`（修复）/ `docs:` / `refactor:` / `chore:`。**周报的功能/Bug 分类完全依赖此前缀。** ✅
2. 一个 PR 只做一件事，必须关联 issue。✅
3. 禁止提交密钥、密码、个人隐私（真实手机号/住址等）。✅
4. 新增依赖需在 PR 中说明必要性，重量级依赖默认拒绝。✅
5. 底层框架（paopao-ce）确定后，补充 Go 与 Vue 的 lint 规则并接入 CI。

## 二、PR 审查机制（三层）✅

```text
第一层 CI（硬门禁）：编译 + 测试必须绿，物理上无法绕过
第二层 AI 审查（24/7）：按仓库 CLAUDE.md 标准出具 🔴必须修/🟡建议/🟢nit
第三层 人工合并：merge 权持有者最终把关
```

- 🔴 级意见必须处理完才能合并；🟡 需回复说明；🟢 自愿。
- main 分支保护：禁直推、禁 force push、线性历史、仅 squash 合并。✅（含管理员）

## 三、贡献度与晋升制度（抗刷版）

**原则：AI 供数，人供权。** 数字公开透明，晋升最后一步是制度化的人工确认。

1. AI 审查对每个 PR 标注**难度分级：S（小）/ M（中）/ L（大）**——公示信息，不作为任何自动解锁的货币。
2. 晋升路径与硬条件：

| 晋升 | 硬条件（可机器核验） | 最终确认 |
|---|---|---|
| 外围 → 贡献者 | 1 个 PR 被合并 | 自动 ✅ |
| 贡献者 → 审查员（获得 merge 权） | ① 已合并 PR ≥ 5；② 其中 ≥ 1 个 M 或 L 难度；③ 参与 review（有效审查意见）≥ 3 次 | 技术委员会/维护者确认 |
| 审查员 → 维护者 | 委员会提名 | 社区负责人任命 |

3. 周报每周五 20:00 公示**贡献榜**（已合并 PR 数、难度分布、review 参与数）。✅
4. 反刷分条款：拆分同一工作为多个 PR 的，审查员可合并计数；难度标注与实际不符的，以人工复核为准。

## 四、周报机制 ✅

- 每周五 20:00 自动生成：功能更新 / Bug 修复 / 其他改进 / 贡献榜 / 进行中 PR。
- 用途：老师上线决策的依据（本周合并内容均已经 CI + AI 审查）。
- 归档于 `docs/weekly/`，作为社区贡献台账永久保存。

## 五、测试、部署与上线流程

```text
merge → test 环境自动更新（每 10 分钟拉取）→ 内测验收
     → 负责人验收 + 老师决策 → 打 Release tag → 生产环境拉取 tag 部署
     → 回滚：生产重跑上一个 Release tag
```

- test 与生产**强制分离**，生产只部署 Release tag，不追 main。
- 生产部署启用 GitHub Environments 批准制：负责人（可含老师）点击批准后方可执行。

## 六、数据库与数据安全

1. 数据库结构变更只能通过迁移文件（migration），禁止直改生产库。paopao-ce 栈确定后补充具体迁移规范。
2. 迁移前必须备份；备份文件权限 600，存仓库外。
3. 密钥管理：一律进环境变量/secret store，绝不入库；仓库开启密钥扫描与推送保护（待管理员在 Settings → Code security 勾选）。
4. 未成年人社区：用户数据最小化收集；导出/共享用户数据需负责人批准。

## 七、技术资产沉淀

- 部署文档、API 文档、架构说明统一存放 `docs/`，随代码走 PR 流程。
- 技术委员会（拟）：架构与重大方案评审、规范维护、上线审查、新人指导。
